# Two-worker paced latency investigation — 8 October 2026

Local qualification is complete; the selected fix is integrated in source, not deployed. Production remains
migration.4. The preceding [worker audit](MULTIWORKER-2026-10-08.md) retained a
paced mixed-load regression and left rollout qualification incomplete.

## Isolation before editing

The comparison pins bulk to four independent carriers, so ordinary pool
selection does not explain changing placement here. All experiments keep the
same adaptive transport profile, two backend capture workers, source ports,
S/PA flags, null encryption and separate CPU role sets. Each uses the shared
machine test reservation and a fresh result directory.

Two ablations start from a9a111a: restore only the old KCP postprocessing loop,
or restore only the old TCP peek/queued-byte read path. Six profiling comparisons
use 60 seconds warmup and 20 seconds measurement. Their profiles capture the
first ten seconds of warmup; final qualification runs leave profiling disabled.
They are screens, not proof that every observed difference is caused by code.

* Reverting KCP output batching: mean 959 → 1012 µs, p99 6 → 5 ms.
  Average latency worsened about 5.6%; there is no convincing overall benefit.
  Preserve bounded FIFO batching and reusable descriptors.
* Restoring the TCP peek: mean 1039 → 954 µs, p99 8 → 6 ms with role clocks
  within 5%. This suggests the empty TCP poll path is worth investigating.
* Fresh receive.4/integration pair: mean 1017 → 986 µs, p99 6 → 5 ms, but
  integration has appreciably higher client/server clocks. The earlier adverse
  receipts remain valid evidence; this unmatched pair does not clear the gate.

## Direct-read candidate

Exploration source 8f1ca0f replaces the ioctl/read pair with one nonblocking
read attempt. Instead of querying TIOCINQ every time, each relay starts with the
existing 4 KiB pooled class, doubles after a full read, and shrinks one class
when a successful read fills at most one quarter. The existing 64 KiB maximum
remains. Hysteresis avoids adjacent-class oscillation. Only the next size hint
stays with the relay; pooled scratch returns before an idle netpoll wait and
after its destination write. No YAML or retransmission settings change.

The earlier no-peek implementation still executed two syscalls on an empty poll
attempt and temporarily borrowed a 32 KiB buffer before EAGAIN. Restoring the
peek avoids that idle work but adds a syscall for every successful payload.
Direct reading removes the queued-byte query on both paths. This is an identified
avoidable cost; the exact contribution to earlier tail variation is not isolated.
Application bytes, EOF/half-close, cancellation, bounded scratch classes and
outer packet encoding must remain unchanged.

The engine race suite passed, including a new varying-burst exact-byte/EOF
regression. Eight no-profiling workloads compare the unchanged integration
candidate with direct reading in two alternating pairs for each mixed case.
Paced medians: mean **1020 → 940 µs**, p99 **7.5 → 6 ms**, requests/s
**1868 → 1938**. The first paced pair matches all role clocks within 5%; the
second candidate runs at lower server/workload clocks and has mean 955 µs,
p99 6 ms versus 962 µs/6 ms for its control. Both retain offered bulk.
Saturated medians: mean **801 → 804 µs**, p99 **8 → 6.5 ms**, requests/s
**4985 → 4973**. Both saturated pairs match role clocks within 5%. All HTTP
warmup/measurement errors are zero, both workers handle packets, and cleanup
passes. Do not infer universal superiority from these finite runs.

A clean final native build from 8f1ca0f is
enterprise-2026.10.08-latency.1, SHA-256
8b538459fa7252afbd38a32161bf69dd2f7270ffc537ea519b0718c244f1209e.
Four additional paced runs compare it with receive.4. Median mean improves
**1052 → 956 µs**, with p99 bounds **5.5 → 6.5 ms**. The first pair matches
all role clocks within 5%; the second candidate's server clock is about 5.7%
lower. These satisfy the earlier 5% mean / 2 ms p99 allowance, rather than
claiming the candidate always has a lower tail than the control.

## Final throughput, WAN and lifecycle results

Two alternating clean bulk pairs per capture-worker count include the original
adverse first pair and a reverse-order repeat. These are uncapped, unencrypted
links with no injected delay/loss/rate cap and four pinned carriers.

| Capture workers / direction | Unchanged integration | Direct-read candidate |
|---|---:|---:|
| One / upload | 4.786 Gbit/s | 4.723 Gbit/s |
| One / download | 3.487 Gbit/s | 3.480 Gbit/s |
| Two / upload | 5.704 Gbit/s | 5.688 Gbit/s |
| Two / download | 4.450 Gbit/s | 4.442 Gbit/s |

Two-worker medians differ by less than 0.3%; single-worker medians by at most
1.3%. The first single-worker upload was about 3% lower; the reversed pair was
slightly faster for the candidate. These finite pairs do not demonstrate a
substantial persistent bulk penalty, or mathematically zero performance cost.
All original measurements, CPU placement, adaptation/configuration and resource
samples remain in the [forty-workload ledger](latency-qualification-2026-10-08.json).

Unpinned 64-worker HTTP churn measures **13,363 → 13,587 requests/s**, zero
errors and unchanged p99 **11 ms**. All 10,000 predominantly idle held TCP
connections return verified responses. Client peak RSS is **206.1 → 204.9 MiB**,
server **201.0 → 196.9 MiB**, with zero swap. A hint can choose a larger scratch
class than the current queued payload; its bound remains 64 KiB and idle relays
hold no checked-out scratch. These held-flow numbers are not busy-user capacity.

Representative WAN pairs pass byte integrity, HTTP/body correctness and exact
cleanup. High-delay HTTP mean is **508.5 → 502.9 ms**, asymmetric HTTP mean
**94.15 → 93.97 ms**, and mobile/lossy HTTP mean **141.0 → 145.3 ms**, p99
**608 → 569 ms**. These are supplementary short pairs, not proof of universal
link superiority. Existing KCP pacing/window/retransmission settings are unchanged.

The 20-second reordered-body result is adverse: goodput
**88.565 → 82.868 Mbit/s** (-6.4%), mean **1493.8 → 1610.7 ms**. It remains
visible. A fresh reverse-order comparison with **60 seconds per HTTP/body phase**
measures body goodput **79.855 → 88.124 Mbit/s**, mean **1672.4 → 1513.2 ms**;
HTTP mean **89.14 → 88.06 ms**, with zero errors. Prior unchanged integration
reordering receipts themselves span about 7% variation. Different durations are
not pooled into a favorable median. The evidence does not show a consistent
reordering deficit; it also does not erase the short adverse sample or establish
that every future replay will improve.

Application `go test -race -count=1 ./...` and `go vet ./...` pass. Native and
race-instrumented two-worker live reload pass all 19 continuity checkpoints with
64 active streams per original peer, four carriers and three edit cycles.
Both original listeners exercise both workers. The unaffected peer retains all
64 streams without errors, PIDs remain stable, client FDs stay **87 → 87**, and
owned firewall cleanup preserves the unrelated rule. Race logs report no Go
data races. Structural replacements intentionally close the affected peer's
streams as documented; they do not establish seamless structural reload.

Screening CPU profiles account for roughly 43–54% syscall samples. They sample
startup, not the final latency window, and aggregate packet/TCP/poll operations;
this does not isolate ioctl's contribution to the original tail. Profile analysis
ran under the machine reservation before the last performance comparisons.
